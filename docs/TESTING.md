# Test Plan and Results

Run everything with:

```sh
make test
```

## Automated unit tests (`tests/test_board.c`): 45 checks

| Area | What is checked |
|------|-----------------|
| Initialisation | 20 boxes unowned, count 0, board not full |
| Validation | horizontal and vertical neighbours valid; reversed order valid; row 5, column 6 and negative values rejected; same dot rejected; diagonal rejected; distance 2 rejected; repeated line rejected, including in reverse order |
| Single box | first three sides complete nothing; the fourth side completes the box; it goes to whoever drew the **last** side |
| Each side last | box completed with top, bottom, left and right drawn last (covers all 4 branches of `board_apply_move`) |
| Double box | a shared line completes 2 boxes; both go to the same player |
| Full board | drawing all 49 lines claims exactly 20 boxes; the board reports full |
| Turns/scores | A starts; the turn passes after a non-scoring move; the scorer moves again; the score updates |
| Winner | 11–9 → A, 7–13 → B, 10–10 → tie |
| Input parsing | valid input, extra spaces, 3 numbers, 5 numbers, letters, `A0` style, empty line, a 20-digit number (no overflow) |

## Scripted full-game tests (`tests/run_tests.sh`): 9 checks

The move files in `tests/inputs/` were generated by a **separate simulator**
(not by this C program), which also computed the expected result. So these
tests compare the C program against an independent reference.

| File | Moves | Contains double-box moves | Expected result |
|------|-------|---------------------------|-----------------|
| `tie_game.txt` | 49 | yes (4) | A = 10, B = 10, "It's a tie!" |
| `a_wins_game.txt` | 49 | yes (5) | A = 19, B = 1, "Player A wins!" |
| `b_wins_game.txt` | 49 | yes (4) | A = 1, B = 19, "Player B wins!" |
| `invalid_input.txt` | 13 lines | — | 11 "Invalid move" messages, an early-exit message, exit status 1 |

About half of the moves in each file give the dots in reverse order, which
tests the normalisation.
