# Test Plan and Results

Run everything with:

```sh
make test
```

## Automated unit tests (`tests/test_board.c`): 49 checks

| Area | What is checked |
|------|-----------------|
| Initialisation | 20 boxes unowned, count 0, board not full |
| Validation | horizontal and vertical neighbours valid; reversed order valid; row 5, column 6 and negative values rejected; same dot rejected; diagonal rejected; distance 2 rejected; repeated line rejected, including in reverse order |
| Single box | first three sides complete nothing; the fourth side completes the box; it goes to whoever drew the **last** side |
| Each side last | box completed with top, bottom, left and right drawn last (covers all 4 branches of `board_apply_move`) |
| Double box | a shared line completes 2 boxes; both go to the same player |
| Full board | drawing all 49 lines claims exactly 20 boxes; the board reports full |
| Turns/scores | A starts; the turn passes after a non-scoring move; the scorer moves again; the score updates |
| Winner | 11–9 → A, 7–13 → B, 10–10 → tie |
| Input parsing | valid input, spaces and tabs, missing whitespace between coordinates, 3 numbers, 5 numbers, letters, `A0` style, empty line, a 20-digit number (no overflow) |

## Scripted full-game tests (`tests/run_tests.sh`): 9 checks

The move files in `tests/inputs/` were generated by a **separate simulator**
(not by this C program), which also computed the expected result. So these
tests compare the C program against an independent reference.

| File | Moves | Contains double-box moves | Expected result |
|------|-------|---------------------------|-----------------|
| `tie_game.txt` | 49 | yes (4) | A = 10, B = 10, "It's a tie!" |
| `a_wins_game.txt` | 49 | yes (5) | A = 19, B = 1, "Player A wins!" |
| `b_wins_game.txt` | 49 | yes (4) | A = 1, B = 19, "Player B wins!" |
| `invalid_input.txt` | 13 lines | — | 11 "Invalid move" messages, an early-exit message, exit status 1 |

About half of the moves in each file give the dots in reverse order, which
tests the normalisation.

Every scripted check verifies the game's exit status as well as its output.
Completed games must exit with status 0; the early-end-of-input fixture must
exit with status 1. Output is captured before checking it, so an early exit
from `grep -q` cannot interrupt the game through its output pipe.

The four additional parsing checks were added after the Alpine screenshots
below were taken. Those screenshots document the original 45 checks.

## GitHub Actions

The `Sprint 1 Alpine checks` workflow builds the current commit inside an
Alpine 3.24 container on every push and pull request. It runs `make test`,
`make test-game`, `make valgrind`, and a batch GDB session that stops in `board_apply_move`,
prints the move, and shows the call stack. Results are available in the
repository's Actions tab. VM boot and restart behaviour still need to be
checked in VirtualBox.

## End-to-end console game checks

Install Python 3 (`apk add python3` on Alpine), then run `make test-game`.
Python is used by these tests only; the game itself remains a C executable.

`tests/test_game.py` checks 107 scenarios through the compiled game's standard
input and output. Its reference model stores geometric edges in a set and
scans all 20 boxes after every legal move. This is independent of the C
implementation's horizontal/vertical arrays and adjacent-box lookup.

- Three existing fixtures cover an A win, a B win, and a tie.
- One hundred seeded complete games exercise 4,900 legal moves, including
  reversed endpoints, spaces and tabs, and zero-, one-, and two-box captures.
- Every displayed board, box owner, score update, turn prompt, extra turn,
  final result, and process exit status is compared with the reference model.
- Invalid inputs are interleaved throughout the complete games. These cover
  missing and extra numbers, joined coordinates, letters, decimals, enormous
  numbers, lines longer than the input buffer, off-board dots, identical dots,
  diagonals, distant dots, and repeated edges in reverse order. Rejection must
  preserve the player and allow the subsequent legal move to succeed.
- Four incomplete games check end-of-input before play and after 1, 10, and
  48 moves, including input without a final newline.

GitHub Actions also runs Valgrind on both winning fixtures and the unit-test
binary, in addition to the tie game covered by `make valgrind`.
